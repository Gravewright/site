    O Gravewright possui três interfaces relacionadas. Elas usam as mesmas verificações nativas de permissão, mas têm marcadores de versão, assinaturas e formatos de resposta diferentes:

    InterfaceEntradaMarcador atualUso previsto
    Pythonfrom api import actors, ...api.API_VERSION == "1.0"Integrações confiáveis no servidor com Django inicializado
    API de domínio no navegadorwindow.gravewright ou api do contexto do móduloapi.version == "1.2.0"Frontend nativo e extensões de navegador
    Operações originais de móduloshost.call(name, payload, options) do bloco montadoSDK 1.0.0Módulos de navegador instalados e ativos

    A fachada Python reexporta funções selecionadas dos serviços; não descobre plugins nem registra apps Django. As APIs do navegador fazem requisições autenticadas a esses serviços. O registro original do SDK é menor e possui schemas JSON explícitos. Não reutilize payloads entre api.actors.update(...) e host.call("actor.update", ...) sem conferir seus contratos. O projeto não distribui atualmente SDK npm, especificação OpenAPI nem verificador automático de compatibilidade entre versões. Os marcadores descrevem este checkout, sem garantir estabilidade de detalhes internos não documentados. Consulte o licenciamento.

    API de domínio no navegador

    O template base carrega frontend-api.js. Após o carregamento, use a API vinculada à mesa na página de jogo ou selecione uma mesa explicitamente:

    javascript
    const table = gravewright.forTable("<uuid-da-campanha>");
const actors = await table.actors.list();
const result = await table.dice.roll("1d20+3", { label: "Teste" });

    Substitua o UUID por uma campanha da qual o usuário autenticado participe. Rolagens publicam uma mensagem de chat; dice.roll não é uma calculadora somente de leitura. Um módulo deve usar sua api fornecida para manter as requisições vinculadas à ativação e montagem.

    forTable(tableId, {sceneId}) fixa a cena. Um sceneId/mapId conflitante em payload posterior gera stale_context. Na página de jogo, a API sem cena fixa pode usar o mapa selecionado; integrações que precisam de identidade estável devem fixá-la. Adaptadores globais de conta/campanha/administração/módulos funcionam sem mesa selecionada; operações da mesa exigem contexto.

    Métodos e payloads

    O mapeamento de métodos para comandos está em contracts/frontend.json; domain-api.js acrescenta atalhos. Validação e projeção de permissões pertencem aos serviços nativos. O contrato é um registro de métodos, não um schema completo de payloads. Exemplos estão nos testes de API frontend, testes dos domínios e testes de cada app.

    Todo domínio abaixo possui state(payload = {}, options) e os métodos listados, normalmente com assinatura (payload = {}, options):

Os resultados incluem snippet autorizado, kind e actions; as referências recentes são revalidadas a cada consulta.

    combat.stop encerra o encontro e limpa os participantes, a iniciativa e o histórico de turnos e rodadas. Os atores e tokens da cena são preservados; adicione participantes novamente antes de iniciar outro encontro.

    Os seis atalhos de transição de combate (nextTurn, previousTurn, nextRound, previousRound, start, stop) também buscam a versão atual quando omitida. Fornecer versões explicitamente permite detectar alterações concorrentes:

    javascript
    const current = await table.actors.get("<uuid-do-ator>");
const requestId = crypto.randomUUID();
await table.actors.update(current.id, {
  name: "Ator renomeado",
  version: current.version
}, { requestId });

    Mutações geram um UUID requestId quando ele não é fornecido. Comandos que usam recibos nativos deduplicam tentativas com o mesmo ID; reutilize-o apenas ao repetir o mesmo comando lógico. Uma nova alteração exige novo ID. version/expectedVersion desatualizada ainda pode gerar conflict. Não presuma idempotência em todos os endpoints: alterações da sala de espera e moderação do chat possuem outras assinaturas de serviço.

    options.signal cancela operações pendentes. Um contexto descartado resulta em stale_context; cancelamento explícito resulta em cancelled nas operações com escopo do módulo. Trate error.code, não textos traduzidos. Falhas autorizadas dos serviços nativos também podem fornecer uma mensagem em error.message; exiba-a como texto pelo Translator. Adaptadores HTTP globais também podem expor erros de transporte/autenticação dos endpoints.

    Descoberta de capacidades e domínios adicionais

    api.capabilities() retorna uma cópia independente do contrato local do navegador, incluindo métodos, leituras, transportes binários e operações demoradas. A seção global lista os adaptadores exclusivos da página para contas, campanhas e administração; não os concede a uma montagem de módulo. Não faz requisições nem concede permissões. Em Python, api.capabilities() retorna {pythonVersion, browser} sem acessar o banco. As operações do sistema atual são descobertas por await api.system.state().

    Os novos domínios mantêm campanha, verificações de mestre, UUIDs de operações e revisões esperadas dos serviços nativos. Os payloads públicos usam estes nomes:

    OperaçãoPayload
    mapBuilder.state / read{} / {projectId}
    mapBuilder.save{projectId, expectedVersion, document, folderId?}; na criação, use UUID novo e expectedVersion: 0
    mapBuilder.generate{projectId, expectedVersion}; cria uma cena privada
    mapBuilder.update / sync{projectId, expectedVersion, expectedSceneVersion}
    mapBuilder.adopt{sceneId, expectedSceneVersion}
    blueprints.state{sceneId}; rede de automações autorizada
    blueprints.save{sceneId, elementId, expectedVersion, expectedProjectVersion, blueprint}
    blueprints.templates / readTemplate{} / {templateId}
    blueprints.saveTemplate / deleteTemplate{templateId, expectedVersion, name, description, definition} / {templateId, expectedVersion}
    blueprints.test{sceneId, elementId, expectedVersion, event, tokenId?, blueprint?}
    blueprints.testDraft{document, elementId, event, actorId?, projectId?}; um projeto vinculado autorizado fornece o escopo da cena original para vínculos de relógios, pistas e mapas mentais no ensaio temporário
    blueprints.control{sceneId, elementId, expectedVersion, action, value?}
    maps.exportUniversalVtt{sceneId}; JSON nativo de intercâmbio
    maps.navigate{mapId}; mapId: null explícito volta a seguir a transmissão em contexto sem cena fixa
    maps.activate{mapId, playerIds?}; exclusivo do mestre. Omita playerIds para ativar para todos e remover destinos individuais. Um array não vazio de IDs de usuários jogadores da campanha, sem duplicatas, muda somente esses destinos. O estado de mapas do mestre inclui players: [{id, name, color, sceneId}]; os demais papéis não recebem essa lista.
    library.createFolder{name}; retorna {ok, id}
    library.updateFolder / deleteFolder{folderId, name} / {folderId}
    library.move / delete{assetId, folderId} / {assetId}; aliases nativos snake_case continuam aceitos
    ownership.read / state{kind, id}; revisão, níveis, permissões e membros para o mestre
    ownership.update{kind, id, version, permissions, reset?}; mantém as regras nativas de lote/páginas

    Os tipos de ownership são actors, items, journals, scenes, cards, compendiums, tokens, pages e os grupos actor-folders, item-folders, journal-folders, scene-folders. A página usa ID journalUUID:sectionId; revisões de pastas em lote são strings opacas. Nenhum método novo substitui silenciosamente uma revisão fornecida. Atualizações do Builder também conferem a cena gerada com a cena autoritativa da montagem. Ensaios mantêm o rollback nativo.

    Renderização e criação de tiles ocorrem fora de uma transação global do transporte; cada serviço mantém seus próprios limites de commit e limpeza. Geração, atualização de cenas, exportação UVTT e ensaios começam sem prazo artificial no cliente. options.timeoutMs define um prazo; null o desativa. As coleções do Builder usam as invalidações existentes de mapas. Relógios e pistas possuem os eventos de coleção descritos abaixo.

    Relógios de progresso

    O domínio clocks fornece os mesmos registros persistentes na mesa e no gestor de campanha. state({sceneId}) retorna os relógios da campanha e daquela cena autorizada, filtrados pela participação atual. O adaptador nativo da página usa a rota GET de estado dos recursos para espectadores visualizarem relógios públicos.

    Criar aceita {name, description?, segments?, value?, color?, visibility?, playersCanEdit?, pinned?, scopeSceneId?}. Os padrões são 4 segmentos, valor 0, #c9a44c, gm, false, false e escopo da campanha. Segmentos são inteiros de 2 a 24; o progresso vai de 0 ao total de segmentos; cada campanha comporta até 128 relógios. Atualizar aceita os campos de configuração e o id e a version existentes. advance({id, version, delta}) aceita delta inteiro de -24 a 24 e limita o progresso ao intervalo válido. Reiniciar e excluir aceitam {id, version}. Somente mestres configuram, reiniciam ou excluem; jogadores avançam apenas relógios públicos com playersCanEdit: true. Espectadores continuam somente com leitura. Os relógios retornados expõem canEdit, canConfigure e o escopo salvo em sceneId.

    description é texto autoral opcional com padrão "" e exige string de até 4.000 caracteres. Somente configurações do mestre o alteram. Atualizações que omitem o campo o preservam; leitores só o recebem quando podem ver o relógio. O campo é adicional, sem novo método de navegador ou versão do SDK.

    scopeSceneId: null salva o escopo da campanha; um UUID de cena salva o escopo da cena. O sceneId/mapId da requisição é o contexto de visualização e nunca move o relógio. Uma API vinculada a cena rejeita outro scopeSceneId não nulo. Alterações de relógios existentes exigem a versão salva; conflitos exigem revisar o estado atualizado. O evento clocks.changed usa o envelope de estado de recursos descrito abaixo. Consulte o guia de relógios para visibilidade, fixação e sincronização.

    Descoberta de pistas

    O domínio clues compartilha as descobertas persistentes entre a mesa e o gestor de campanha. state({sceneId}) retorna as pistas da campanha e daquela cena autorizada. Jogadores e espectadores recebem somente pistas com visibility: "players" e value === segments; pistas não descobertas não têm registro, título, conteúdo, ID ou marcador público. gmNotes fica ausente de todas as projeções públicas, inclusive após a descoberta. Toda alteração direta exige a autoridade atual de mestre.

    Criar aceita {name, content?, gmNotes?, segments?, value?, color?, visibility?, pinned?, scopeSceneId?}. Os padrões são conteúdo e notas vazios, 4 etapas, valor 0, #c9a44c, players, false e escopo da campanha. Nomes têm até 120 caracteres; conteúdo e notas do mestre têm até 4000 cada. Etapas são inteiros de 1 a 24; o valor vai de 0 ao total. Uma etapa permite descoberta imediata. Cada campanha comporta até 128 pistas, independentemente dos relógios.

    Atualizar aceita esses campos e {id, version}. advance({id, version, delta}) aceita inteiro de -24 a 24 e limita o progresso. reset({id, version}) zera o progresso e preserva a visibilidade; hide({id, version}) restringe a mestres e preserva o progresso; reveal({id, version}) completa a descoberta e permite visibilidade aos jogadores. Excluir aceita {id, version}. Versões e UUIDs de tentativa seguem os recibos nativos; um antigo mestre não pode reutilizar um recibo privado após perder a autoridade.

    scopeSceneId controla o escopo salvo; sceneId/mapId fornece o contexto de visualização, como nos relógios. Leituras nativas usam a rota GET compatível com espectadores. Assinaturas de clues.changed releem o estado projetado no envelope de recursos abaixo. O nó clueControl do MapBuilder delega somente o efeito configurado e não concede alterações diretas aos jogadores. Ensaios desfazem suas alterações e notificações. Veja pistas para uso e ações do nó.

    Mapas mentais colaborativos e vínculos tipados

    O domínio mindmaps lê grafos compartilhados pelas permissões atuais de cada pessoa. Não usa a cena atual implicitamente: state({}) lista todos os mapas acessíveis; state({sceneId}) seleciona mapas de campanha e daquela cena. Módulos vinculados explicitamente a uma cena mantêm esse contexto autoritativo.

    MétodoPayload e resultado
    state / read{sceneId?} / {id, sceneId?}; envelope da coleção / um mapa projetado
    resources{query?, kinds?, limit?, sceneId?}; {kinds:[{id,label}], resources:[...], truncated}
    resolve{reference}; exibição autorizada atual de um recurso ou null para destinos ausentes/negados
    create{name, visibility?, editorIds?, scopeSceneId?, document?}; exclusivo do mestre, padrão privado e escopo de campanha
    update{id, version, name?, document?, visibility?, editorIds?, scopeSceneId?}
    node{id, version, nodeId, patch}; altera os campos informados de um tópico
    delete{id, version}; exclusivo do mestre

    visibility é gm ou players. editorIds contém UUIDs de jogadores atuais da campanha; selecionados leem/editam mesmo mapas privados. Todos os mestres editam, e a visibilidade pública concede somente leitura aos demais. Jogadores alteram name, document e campos dos tópicos; escopo/acesso continuam exclusivos dos mestres. Streamers não escrevem. Escritas retornam {id, version, mindmap} (excluir retorna {id}), usam recibo separado e exigem a versão salva para mapas existentes. Conflitos exigem revisão do estado atual sem trocar silenciosamente a versão esperada do rascunho. mindmaps.changed usa o envelope de recursos.

    O documento é {nodes, edges}. Tópicos têm UUID id, parentId opcional, label, notes, color hexadecimal, x, y, collapsed, completed e links. Vínculos de pais formam uma floresta sem ciclos. Arestas adicionais são {id, from, to, label?} entre tópicos existentes. Patches aceitam esses campos dos tópicos, exceto id. Os limites são 64 mapas por campanha, 500 tópicos/1.000 arestas por mapa, 16 vínculos por tópico/2.048 no total e 1 MiB por documento. Títulos têm 240 caracteres, notas 8.000 e coordenadas ficam entre ±100.000.

    Referências canônicas são exatamente {kind, id, pageId?}. O registro de recursos define 37 tipos, incluindo IDs numéricos nativos, entradas de compêndios instalados (packId/entryId), páginas (id: journalId com pageId) e desenhos (sceneId/drawingId). Descubra os tipos por resources, sem inferi-los pelos rótulos. A busca aceita até 120 caracteres; limit tem padrão 80 e intervalo 1–200. Rótulos vêm das projeções nativas atuais. Nomes autorais ficam literais; labelKey/descriptionKey opcionais identificam textos gerados para o Translator.

    Vínculos ausentes e negados são projetados igualmente como {unavailable:true, key}, sem tipo/ID/nome/URL ocultos. Devolva o marcador opaco intacto ao editar outros conteúdos ou omita-o para remover o vínculo. Ele não autoriza criar uma referência oculta. Abrir novamente revalida as permissões; nomear o destino ou compartilhar um mapa não concede acesso ao recurso. Veja Mapas mentais para tipos, colaboração, nós do MapBuilder e remapeamento tipado dos arquivos.

    Vínculos de recursos nos diários

    api.journals.resources({query?, kinds?, limit?, sceneId?}, options) busca no mesmo catálogo tipado de campanha dos mapas mentais. api.journals.resolve({reference}, options) devolve {resource: row | null} após verificar o acesso atual ao destino. Ambos são métodos de leitura disponíveis a jogadores e streamers autorizados. Leituras sem cena vinculada não herdam a cena transmitida; uma cena explicitamente vinculada continua sendo a autoridade.

    O texto mantém gw-journal-doc-v1, versão 1. A referência é um átomo inline:

    json
    {"type":"gwResourceLink","attrs":{"reference":{"kind":"journal-page","id":"<journalUUID>","pageId":"page_main"}}}

    O vínculo salvo contém apenas kind, id e pageId opcional. A projeção de cada destinatário acrescenta metadados atuais e uma key opaca; destinos sem acesso tornam-se {unavailable:true,key}, sem identidade ou título. Devolva o marcador intacto para preservá-lo numa edição autorizada. Ele está vinculado ao diário de origem e não cria uma conexão privada nova. Cada diário aceita até 512 referências; os limites normais de tamanho e profundidade também se aplicam. O salvamento usa a versão e o UUID de operação existentes do diário.

    As leituras nativas usam GET /api/containers/{campaign}/journals/resources com parâmetros query, kinds (array JSON), limit e sceneId opcional, e GET /api/containers/{campaign}/journals/resolve?reference=<JSON>. As respostas são privadas e não ficam em cache. Pacotes Python usam api.journals.resources(campaign_id, user_id, *, query='', kinds=None, limit=80, scene_id=None) e api.journals.resolve(campaign_id, user_id, reference). A busca não muda a presença ou navegação na mesa. Veja Diários e referências para edição, acesso e cópias portáteis.

    Capítulos e páginas dos diários

    Atualizações usam o comando existente do diário, a versão esperada e o UUID de operação. O payload data pode incluir capítulos independentes, inclusive vazios:

    json
    {
  "chapters": [
    {"id":"chapter_main", "name":"Chapter one", "parentId":null, "sortOrder":10},
    {"id":"chapter_child", "name":"A subchapter", "parentId":"chapter_main", "sortOrder":10}
  ],
  "sections": [
    {"id":"page_main", "title":"A page", "kind":"text", "chapterId":"chapter_child"},
    {"id":"page_loose", "title":"An ungrouped page", "kind":"text", "chapterId":null}
  ]
}

    Cada página pertence a nenhum ou a um capítulo. Cada capítulo tem nenhum ou um pai e pode conter de zero a várias páginas e subcapítulos. Os IDs são locais ao diário; copiar uma campanha os preserva sem tratá-los como UUIDs de recursos. IDs de capítulos são únicos, com 1–40 letras ASCII, números, sublinhados ou hífens; nomes têm 1–80 caracteres. O servidor permite até 128 capítulos, oito níveis e as 64 páginas existentes. Pais ausentes, ciclos e vínculos de página para capítulos inexistentes são rejeitados antes de salvar. sortOrder ordena capítulos dentro de cada pai.

    A projeção autorizada expõe chapters junto com sections. Páginas privadas continuam filtradas, assim como os ramos compostos apenas de páginas sem acesso. Ancestrais de páginas legíveis e ramos realmente vazios permanecem visíveis. Apresentações de uma página incluem apenas seu caminho de capítulos. Atualizações preservam as páginas ocultas protegidas pelo servidor e a estrutura necessária para esses vínculos.

    Nomes legados de sections[].category recebem IDs estáveis na normalização; category permanece como espelho do nome para compatibilidade. Um chapterId: null explícito remove o vínculo da página. Atualizações antigas que omitem chapters mantêm os capítulos existentes, inclusive vazios. O histórico e os arquivos portáteis da campanha preservam a árvore.

    Operações dos sistemas e PDF System

    O host encaminha api.system.call(name, data, options) somente ao provedor do sistema atual da campanha. Nome ou payload não selecionam outro sistema. Pacotes confiáveis de servidor registram callbacks no AppConfig.ready() com api.systems.register_api(system_id, operations). Cada entrada declara {effect: "read" | "write", handler, description?}, sem consultar o banco no registro. O handler recebe (campaign_id, user_id, payload, request_id, scene_id) e controla validação dos recursos, transações, revisões, recibos e notificações. O host verifica participação atual, limita o JSON, impede trocar a cena montada e rejeita escritas de streamers antes de chamar o handler.

    campaigns.management(id, options) lê o resumo da campanha exclusivo do mestre sem carregar a mesa nem entrar em sua presença. A área de gerenciamento usa os mesmos serviços nativos de documentos e verifica o vínculo atual de mestre daquela campanha.

    As ferramentas de preparação usam outros métodos exclusivos do mestre. preparation(id) lê planos de sessão, eventos da cronologia, o painel de quem chama, pendências e o diagnóstico de fichas do sistema. prepare(id, action, payload, requestId) executa um comando: session-create, session-update, session-finish, session-reopen, session-delete, event-create, event-update, event-delete ou board-update. Repetir o mesmo comando reutiliza seu UUID de requisição. Alterações e exclusões enviam a revision atual do registro; uma revisão desatualizada é recusada com HTTP 409. references(id, type, documentId) lista os vínculos e usos de um personagem, item, diário ou cena. viewAs(id, userId) devolve as projeções nativas de diários, atores, itens e cenas que um jogador recebe. journalHistory(id, journalId), journalRevision(id, revisionId) e journalTrash(id) leem versões de diários, uma comparação linha a linha com a versão atual e os diários excluídos. Requisições de preparação recusadas informam o motivo no campo JSON error.

    Payloads de preparação usam estes campos nativos. Criar retorna {id, revision}; alterar o painel retorna {revision}. Campos omitidos em atualizações preservam seus valores atuais.

    AçãoPayload

    session-reopen / session-delete{id, revision}
    event-create / event-update{title, worldDate?, position?, date?, upcoming?, description?, links?}; atualizar também exige {id, revision}
    event-delete{id, revision}

    Uma etapa usa {id, kind, refId, label, done}; kind pode ser actor, item, journal, scene, encounter, track, playlist ou note (notas usam refId: null). Um item de checklist usa {id, text, done}. Vínculos de eventos e itens fixados usam {type, id} para os mesmos tipos, exceto note. Datas usam YYYY-MM-DD ou null; datas do mundo continuam texto.     Permissões de proprietário e gerenciamento da campanha continuam verificadas no servidor. Os métodos usam cookies de sessão e obtêm token CSRF antes de escrever. Não há autenticação por chave de API nessa interface. Views e testes dos apps definem os payloads; não coloque credenciais no código de módulos.

    O cabeçalho da biblioteca usa POST /api/admin/updates/notification, exclusivo do proprietário, com JSON vazio e o token CSRF normal. A resposta compacta inclui status, available, versões instalada/disponível e seus rótulos, channel, checkedAt e a URL interna de Atualizações. Ela reaproveita o cache de consulta por 24 horas; consultas simultâneas com cache expirado recebem checking enquanto uma requisição atualiza os metadados. A rota não inicia instalação nem expõe artefatos da release ou erros internos.

Sistemas e Módulos usam essa seleção na instalação. Sem latest=1, a rota continua retornando todas as releases compatíveis e não revogadas; a instalação por versão exata continua disponível.

    GET /api/admin/status inclui updates.installedRelease com version, name completo, notes, url canônica do GitHub e source (bundled, published ou metadata). Respostas de verificação explícita incluem a mesma apresentação. As notas locais estão disponíveis sem consulta ou acesso à rede e não são gravadas no cache de atualização. As notas têm limite de 128 KiB em UTF-8; a versão numérica e as regras de comparação são independentes do nome exibido.

    Transações e hooks do servidor

    Wrappers públicos preservam transações, permissões, versões, recibos de deduplicação onde implementados e notificações após commit. Reverter uma transação externa descarta a escrita e suas notificações pendentes. Escritas ORM diretas não equivalem a essa API de mutação.

    Conecte hooks confiáveis ao sinal Django:

    python
    from api.events import resource_changed

def observe_change(sender, change, **kwargs):
    # sender é o nome do recurso; change contém IDs, não um snapshot.
    print(change.resource, change.action, change.request_id)

resource_changed.connect(
    observe_change,
    dispatch_uid="example.observe-change",
    weak=False,
)

    Registre receivers uma vez em AppConfig.ready() de seu app explicitamente instalado. Change contém campaign_id, user_id, resource, action e request_id.     Transporte e manutenção

    O endpoint de domínio do host é POST /api/tables/<table_id>/api; módulos instalados usam POST /api/tables/<table_id>/modules/<module_id>/api. Recebem {domain, method, payload, requestId?} e retornam {value}. Módulos também enviam mountId, moduleSetRevision e sceneId opcional; a ponte abre o lease antes. Métodos binários usam o sufixo /files correspondente, com metadados JSON no campo multipart metadata e o arquivo em file; downloads retornam bytes. O SDK antigo usa o mesmo prefixo do módulo com /call e envelope {name, payload, ...context}. As URLs descrevem a implementação para mantenedores; módulos devem usar as APIs fornecidas.

Ao adicionar operação no SDK original, atualize schemas, registro, constantes de operações, dispatcher e testes em conjunto; não existe gerador genérico para todos esses arquivos.
