    Os 49 tipos de nó de Blueprint, com exemplos completos

    Configuração concreta e grafo validado para download de cada NODE_TYPES, de event a cooldown.

    Um exemplo para cada node.type

    Os 49 tipos abaixo vêm de NODE_TYPES na revisão documentada. Cada link fornece um documento Blueprint v2 completo e validado, com caminho que alcança o nó apresentado. O trecho exibido é o nó central; o download inclui evento, conexões e consumidores necessários.

    Estes JSONs descrevem o subdocumento Blueprint v2 armazenado pelo host. São fixtures para desenvolvimento: não são módulo instalável, projeto completo do Builder ou arquivo de campanha. Recrie os nós no editor ou use os arquivos em testes isolados de contribuição ao host. Este guia não presume um botão de importar JSON no editor de Objetos Inteligentes.

    Baixe o pacote completo de exemplos ou o validador. Todos os exemplos usam dados sintéticos originais. O avaliador Python interno serve ao desenvolvimento do código-fonte; módulos de navegador devem usar o SDK público.

    Como usar e conferir os exemplos

    No editor, crie o tipo de objeto compatível e os nós do grafo baixado; vincule recursos pelos seletores reais. IDs dos arquivos são sintéticos. O validador testa a forma e o avaliador prevê ações, mas não resolve permissão, existência de recurso ou compatibilidade do alvo. O grafo setRegion pertence a uma região; setAppearance usa uma referência explícita a uma superfície dinâmica. Selecione alvos reais antes de executar na mesa. Não interprete uma ação prevista como prova de aplicação no servidor.

    Execute a fixture em uma instalação de desenvolvimento

    Extraia o pacote de exemplos em data/blueprint-examples, dentro de um checkout descartável da versão documentada. Na raiz do checkout, execute:

    sh
    uv run --locked python data/blueprint-examples/check-examples.py --host .

    O verificador configura banco em memória, bloqueia consultas ao banco e chama as funções reais clean_blueprint e evaluate_graph. Ele valida os quatro tipos de objeto, os dois tipos de conexão e os 49 tipos de nó, incluindo requestRoll e setQuestStatus. Confere as duas visibilidades de rolagem, os seis status de missão e a continuação da execução sem rolar dados nem alterar diários. Isso verifica o formato e as ações previstas. Use também Test behavior para conferir alvos reais, autorização e a cadeia completa no servidor.

    requestRoll valida expressão de dados, rótulo, visibilidade (public ou gm) e público, mas apenas prevê um pedido. Destinatários elegíveis escolhem rolar na janela nativa; streamers não recebem pedidos. setQuestStatus vincula missão existente da campanha e aceita draft, available, active, completed, failed ou archived. A execução real usa autoridade de GM ativo pelo serviço de diários; jogadores não ganham permissão geral de editar diários. O UUID sintético de resources.quest não comprova que a missão pertence à campanha. Delay é retomado pelo verificador usando a continuação real. Counter é avaliado duas vezes com a memória preservada. Interact, Emit event e Timer são pedidos de execução posterior: o avaliador local não executa grafos receptores. Teleport exige token disparador real; contexto inventado no navegador não autoriza movimento.

    Teste como GM e jogador

    Use Simulate para inspecionar um evento local. Depois use Test behavior para ensaiar pelo servidor; as alterações desse ensaio são revertidas. Gere ou atualize a cena como GM e teste uma cena sintética com GM e jogador autorizado. Confira que streamer não consegue gravar. Ao editar novamente o projeto, use Update scene antes de esperar mudanças no comportamento da mesa.

    Para nós com Target, teste recurso real compatível, UUID ausente e recurso de outra campanha. Para mensagens e diários, teste público trigger e um segundo jogador. Para memória/tempo, repita com o mesmo nó, depois reinicie intencionalmente a memória pelos controles do GM. Consulte o resultado de cada ação em Automation, incluindo ignorados por alvo incompatível.

    Controlar shader no host 0.3.3

    O grafo completo de shaderControl começa em Ao interagir e define a opacidade do shader escolhido como 0.35. No editor do Objeto Inteligente, escolha Adicionar nó → Controlar shader, vincule um shader do mesmo mapa, escolha Opacidade, informe o valor e conecte a saída de execução do evento à ação. Substitua o UUID sintético de resources.shader pelo seletor real de alvos.

    A propriedade escolhida determina o tipo da entrada Valor:

    PropriedadeTipo de valorExemplo
    enabledBooleantrue
    colorText, hexadecimal de seis dígitos#f6c26b
    intensity, opacity, speed, scale, radius, rotation, light_response, light_emissionNumber, dentro dos limites nativosopacity 0.35

    Para um valor variável, adicione Obter variável, selecione Number e conecte sua saída Valor à entrada Valor de Controlar shader. Use Boolean para enabled ou Text para color. Encadeie ações Controlar shader para alterar várias propriedades. Valores conectados também são validados; opacidade acima de 1, nomes de cores e propriedades não suportadas são rejeitados. A ação não substitui código GLSL.

    Use Testar comportamento para inspecionar alterações de shader que são revertidas, depois Testar como jogador para ensaiar interações ou eventos de área sem alterar a cena em uso. Vincule um shader real antes do teste no servidor; o verificador da fixture só valida referências sintéticas e prevê ações. Uma tocha apagada ou camada oculta continua controlando seu shader, preservando a intenção de ativação configurada. Cópias e cenas geradas remapeiam os alvos; editar explicitamente um parâmetro no Builder substitui seu valor em execução, enquanto um parâmetro inalterado mantém o valor automatizado.

    Este nó exige a 0.3.3. As receitas anteriores preservam suas versões mínimas documentadas; não presuma que o grafo novo funciona em um host antigo.
