    How to create a combat tools module

    Build a working encounter laboratory covering participants, initiative, order, flags, turns, rounds and cleanup.

    The project you will build

    Create Combat workshop and operate the native encounter of one disposable scene. Add the two tokens, enter or roll initiative, start, select/reorder participants, advance turns/rounds, then stop and remove participants. The selected RPG system remains responsible for its rules and provider.

    Target host: Gravewright 0.3.0. Actions run only when you click Run action, using the signed-in account. The demonstration panel is English. Each recipe specifies inputs and an observable result.

    1. Create the files

    Create a folder named combat-workshop. Save the complete files below as UTF-8, or download the project. manifest.json belongs at the root. No npm dependencies or JavaScript build is required.

    text
    combat-workshop/
  manifest.json
  main.mjs
  recipes.mjs
  styles.css
  LICENSE.txt

    Keep the scene and two tokens from Token workshop. Run Inspect to copy exact scene/combatant identities. Use tokenId for placed tokens or actorId for actor-only participants. This module supplies no RPG system, catalog or Server Rules companion. Its explicit test formula is an encounter setting on the disposable campaign.

    2. Package, install and activate

    From the project folder, run in PowerShell:

    powershell
    python -m json.tool manifest.json
python -m zipfile -c ../combat-workshop-1.0.0.zip manifest.json main.mjs recipes.mjs styles.css LICENSE.txt
python -m zipfile -l ../combat-workshop-1.0.0.zip

    On Linux/macOS, replace python with python3 in the same commands. The archive listing must show manifest.json at its root. As installation owner, open Inside → Modules → Install module → Install from ZIP, select the ZIP and click Install. As GM, open the campaign, select its Gravewright button → Extensions and Activate version 1.0.0 of Combat workshop. Close that menu and click Combat workshop. See your first module for screen-by-screen instructions.

    The package stays inactive until selected for the table. Test one demonstration extension at a time because their launchers share a position. For changed bytes, increment version to 1.0.1, build another ZIP, install and activate that version; do not edit installed files.

    3. Run each recipe

    Inspect this scene encounter

    Paste the disposable scene ID. It need not contain an encounter yet. Copy combatant IDs from the projected list after adding participants.

    javascript
    async ({api,context,signal},v) => {

  const read={signal};
  const write=()=>{
    if(signal?.aborted) throw Object.assign(new Error('Mount closed'),{code:'cancelled'});
    return {signal,requestId:crypto.randomUUID()};
  };
  try {
    return await api.combat.state({sceneId:v.mapId},read);
  } catch(problem) {
    if(problem.code==='conflict'&&!signal?.aborted) await api.combat.state({sceneId:v.mapId},read);
    throw problem;
  }
}

    Expected result: Encounter version, active/round/turn, configuration and authorized combatants.

    How to verify: Compare with the native Combat tracker. A player must not receive hidden entries or unauthorized resources.

    Add a placed token or an actor to combat

    Use tokenId with the two token IDs from the token tutorial, one run per token. Or use actorId for an actor without a scene token. Each Run action is one operation.

    javascript
    async ({api,context,signal},v) => {
  if(context.role!=='gm') throw new Error('GM required');
  const read={signal};
  const write=()=>{
    if(signal?.aborted) throw Object.assign(new Error('Mount closed'),{code:'cancelled'});
    return {signal,requestId:crypto.randomUUID()};
  };
  try {
    if(!['tokenId','actorId'].includes(v.identityType)) throw new Error('Use tokenId or actorId');
    const identity={[v.identityType]:v.id};
    const before=await api.combat.state({sceneId:v.mapId},read);
    return await api.combat.add({sceneId:v.mapId,version:before.version,...identity},write());
  } catch(problem) {
    if(problem.code==='conflict'&&!signal?.aborted) await api.combat.state({sceneId:v.mapId},read);
    throw problem;
  }
}

    Expected result: A combatant is added without duplicating an existing identity; encounter version advances.

    How to verify: Add two distinct combatants and verify both in the native tracker. Tokens from another scene must be refused.

    Set an explicit encounter initiative formula

    On the disposable encounter only, set the generic dice expression1d20. The selected system owns its default formula/provider; this explicit native encounter override does not implement new RPG rules. Clear the input to use manual mode.

    Expected result: config.formula reflects the chosen expression; system-dependent config.input reports how initiative is entered.

    How to verify: Open Combat settings and inspect the formula. Invalid formulas are rejected without a partial config write.

    Set one combatant initiative value

    Use a participating identity. The recipe follows the current config: text input stays text; numeric/rolled input becomes a finite number. Do not hardcode a system attribute.

    How to verify: Set values12 and8 for two participants and inspect order. Text-mode systems may retain manual order.

    Roll initiative for a chosen scope

    Configure an explicit valid formula first. Missing rolls only unset entries; all rerolls all; npcs uses native player-ownership rules; one uses the supplied participating identity.

    javascript
    async ({api,context,signal},v) => {
  if(context.role!=='gm') throw new Error('GM required');
  const read={signal};
  const write=()=>{
    if(signal?.aborted) throw Object.assign(new Error('Mount closed'),{code:'cancelled'});
    return {signal,requestId:crypto.randomUUID()};
  };
  try {
    if(!['all','missing','npcs','one'].includes(v.scope)) throw new Error('Choose an initiative scope');
    const before=await api.combat.state({sceneId:v.mapId},read);
    if(!before.config?.formula) throw new Error('Configure an initiative formula first');
    const identity={};
    if(v.scope==='one'){
      if(!v.id||!['tokenId','actorId'].includes(v.identityType)) throw new Error('Supply the selected combatant identity');
      identity[v.identityType]=v.id;
    }
    return await api.combat.rollInitiative({sceneId:v.mapId,version:before.version,scope:v.scope,...identity},write());
  } catch(problem) {
    if(problem.code==='conflict'&&!signal?.aborted) await api.combat.state({sceneId:v.mapId},read);
    throw problem;
  }
}

    Expected result: Only the selected scope receives server-side rolls; the native tracker orders results.

    How to verify: Set one manual value, run missing and confirm that value remains. Do not claim a specific random roll result.

    Move a participant up or down

    Use a combatant and run up, then down. Manual reordering preserves the active combatant identity rather than silently granting the turn to another entry.

    Expected result: The selected participant changes position while the active identity is preserved.

    How to verify: Start combat, note the current ID and reorder a different entry. The same participant should remain current.

    The two checkboxes set exact booleans; they do not invert an unknown state. Defeated entries are skipped by forward next-turn processing. Clear both to restore the tutorial participant.

    Start or stop the disposable encounter

    Add at least two participants. Start creates an encounter identity and begins round1/turn0. Stop resets the active cursor/history but retains participants. Use only this tutorial encounter.

    Expected result: start: active true, round1. stop: active false, round0.

    How to verify: Inspect encounterId and the native tracker after each intentional action.

    Advance or return one turn

    Start first. Next advances valid native turn clocks and skips defeated entries. An authorized player may end their own current turn; previous is GM-only and requires history.

    javascript
    async ({api,context,signal},v) => {

  const read={signal};
  const write=()=>{
    if(signal?.aborted) throw Object.assign(new Error('Mount closed'),{code:'cancelled'});
    return {signal,requestId:crypto.randomUUID()};
  };
  try {
    const before=await api.combat.state({sceneId:v.mapId},read);
    if(!before.active) throw new Error('Start combat first');
    const payload={sceneId:v.mapId,version:before.version};
    if(v.direction==='next') return await api.combat.nextTurn(payload,write());
    if(v.direction==='previous'){
      if(context.role!=='gm') throw new Error('GM required for previous turn');
      return await api.combat.previousTurn(payload,write());
    }
    throw new Error('Choose next or previous');
  } catch(problem) {
    if(problem.code==='conflict'&&!signal?.aborted) await api.combat.state({sceneId:v.mapId},read);
    throw problem;
  }
}

    Expected result: Current identity changes according to native order; previous returns the stored cursor when available.

    How to verify: Try next as the current controlling player and a different player. Only the former is allowed. Going back does not resurrect expired conditions or undo periodic effects.

    Stop the disposable encounter and remove its participants one at a time. This removes tracker membership, not the token or actor.

    4. Understand and adapt the complete files

    main.mjs renders the launcher and form. recipes.mjs owns behavior: change the chosen recipe’s run function while keeping its signature. The form passes real number, boolean and File values, blocks overlapping requests and renders using textContent. It does not evaluate user-provided code. api, host, assets and storage belong to the mount; signal cancels work on deactivation. The modal stays open during pending work and is released when the mount aborts. Each business function remains responsible for revisions, permissions and transaction sequencing.

    5. Permissions, failures and final test

    Every write is an explicit Run action. Reads use recipient projections; writes keep native permissions and fresh operation UUIDs. Scene update, object update, token move/configuration and combat use their real revision fields. Some native selection commands have no expected revision parameter in this release; the examples do not invent one. On conflict the recipe rereads current state and stops. Review it, then intentionally run a new operation. Multiple API calls are separate transactions: a completed earlier call is not rolled back if a later read fails. Deactivation aborts scoped work; it cannot undo a server commit.

    Test two participants, player ending their current turn, another player denied, all entries defeated, missing previous-turn history, stale encounter version and abort. Forward clocks can expire conditions or apply system effects. Previous turn/round changes the cursor; it does not undo persisted effects or restore expired conditions. Each participant identity is retained when reordering.
