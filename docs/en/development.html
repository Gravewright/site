    Development

    Development workflow, migrations, generated contracts and release preparation.

    Documentation · Português

    Find the owning layer

    Read architecture and the code map before changing a cross-domain flow. Domain services.py files own authorization, validation and persistence. Views translate HTTP requests and responses; WebSocket consumers translate incoming messages, while realtime dispatch publishes committed changes. Keep business rules in services so browser and Python entry points share the same checks.

    Use the public API when integrating with the core. A Python context identifies a caller; it does not grant authorization. Direct ORM writes are appropriate for controlled migrations/fixtures but can bypass service permissions, revision checks, file cleanup and notifications in ordinary application code.

    For mutations, examine the domain's transaction, request ID and expected-version conventions. Preserve retry behavior and publish committed state. Player and streamer snapshots must exclude hidden data on the server, not merely hide it in the DOM.

    Typical workflow

    bash
    uv sync --locked
uv run --locked python main.py

    Edit the owning service and its views/templates/frontend only as needed. Write a regression test for a changed rule or boundary, and run the relevant test suites. Documentation-only edits usually need link/example review and a focused check, rather than new tests that repeat prose.

    For model changes:

    bash
    uv run --locked python manage.py makemigrations
uv run --locked python manage.py migrate
uv run --locked python manage.py makemigrations --check --dry-run

    Review generated migrations before applying them to valuable data. App labels and model names are also used by portable campaign archives. A schema change may require archive import/export and snapshot tests in addition to model tests.

    Browser contracts and assets

    The browser registry is generated from gravewright/modules/contracts/frontend.json:

    bash
    uv run --locked python scripts/generate_frontend_api.py

    Commit the source contract and generated gravewright/modules/static/gravewright_modules/frontend-contract.js together. The separate SDK contract uses contracts/registry.json, contracts/api.json and the files in contracts/schemas/, including manifest.json. See modules and frontend before changing them.

    Frontend code is native JavaScript modules. Keep lifecycle cleanup explicit for listeners, timers, render objects and asynchronous work. Some third-party bundles have their own build metadata; rebuilding those is separate from launching the Django application. Preserve license banners and update third-party notices when replacing a bundle.

    Documentation conventions

    English guides live under docs/en/; Portuguese guides use the same filename under docs/pt-BR/. Each guide links back to the index and to its translation. Use relative links so documentation works in forks and downloaded source trees. Do not embed a developer's absolute workspace paths or assume a repository URL that is not configured.

    Explain why code exists, its responsibilities and constraints. Keep comments close to the boundary they explain. For important public functions, document accepted identifiers/payloads, return values, side effects and domain errors. Preserve concise existing explanations; do not add a redundant comment to every assignment.

    The existing dice grammar documents are maintained next to their implementation. New project guides should link to those references rather than duplicate syntax rules that can drift.

    Release identifiers

    The current release is 0.3.0. The application manifests use these identifiers, following the formats required by each tool:

    LocationIdentifier
    Full public release nameGravewright 0.3.0 — Alpha
    Application and Runner version0.3.0
    Python project and uv.lock0.3.0
    Frontend package, package lock and update API0.3.0
    Release tagv0.3.0
    Source release artifactGravewright-0.3.0-django.zip

    pyproject.toml is the source of the installed version. gravewright/version.py derives its public identifier and label; keep the frontend package metadata aligned when changing it. API/SDK contract versions and third-party module versions have independent lifecycles.

    Release 0.3.0 follows the stable update-discovery convention for numeric version identifiers; the project remains in Alpha. Administration displays the full release name without a channel selector. Existing host channel preferences and API compatibility are preserved.

    Build a release archive

    Align pyproject.toml, uv.lock, the frontend package.json and its lockfile; add bilingual notes under docs/releases/VERSION.md and update both documentation indexes and READMEs. Build the frontend with node gravewright/maps/scripts/build.cjs, then run the checks in testing, including fresh-install and upgrade scenarios.

    Stage all new source, migration, test and documentation files before packaging:

    bash
    uv run --locked python scripts/build_release.py --check
uv run --locked python scripts/build_release.py

    The builder selects Git-tracked public files, validates version metadata and required files, and writes dist/Gravewright-VERSION-django.zip plus its SHA-256 sidecar. It uses working-tree contents, so publish from the reviewed, committed tree. --include-untracked allows a precommit review snapshot; ignored files remain excluded. Installed extensions, local data, secrets, dependencies and machine-specific launchers are excluded in both modes. Set SOURCE_DATE_EPOCH to a fixed Unix timestamp for reproducible archive timestamps.

    Test an extracted copy of the final ZIP with disposable storage. Publish the matching commit as vVERSION with the ZIP, checksum and bilingual notes. Verify the uploaded asset digest and applicable repository CI workflows; archive creation alone does not validate application behavior or publish a release.

    Before submitting

    Follow CONTRIBUTING.md. Check translated docs, the generated registry, migrations and license notices as applicable. Describe the exact validation performed and any failures. Never include .env, runtime data, private uploads or test browser credentials from a real deployment.
