    All 48 Blueprint node types, with complete examples

    Concrete configurations and downloadable validated graphs for every NODE_TYPES entry, from event to cooldown.

    One example for each node.type

    These 48 types come from NODE_TYPES in the documented revision. Every link provides a complete validated Blueprint v2 document with a path that reaches the sample node. The displayed snippet is the central node; the download includes its event, connections and required consumers.

    These JSON files describe the stored Blueprint v2 subdocument. They are development fixtures, not an installable module, a complete Builder project or a campaign archive. Recreate the nodes in the editor, or use the fixtures in isolated contributor tests. This guide does not assume a JSON import button in the Smart Object editor.

    Download the complete example bundle or the validator. Every example uses original synthetic data. The host's internal Python evaluator is for source development; browser modules must use the public SDK.

    Use and verify the examples

    In the editor, create a compatible owner and the nodes from the downloaded graph; bind resources through real selectors. File IDs are synthetic. Validation checks shape and evaluation predicts actions; neither resolves permissions, resource existence or target compatibility. The setRegion graph belongs to a region; setAppearance uses an explicit dynamic surface reference. Bind actual targets before live use. A predicted action is not proof of server application.

    Run the fixture in a development installation

    Extract the example bundle to data/blueprint-examples inside a disposable checkout of the documented host. From the checkout root, run:

    sh
    uv run --locked python data/blueprint-examples/check-examples.py --host .

    The checker configures an in-memory database, blocks database queries and calls the real clean_blueprint and evaluate_graph functions. It validates all four object kinds, both connection kinds and all 48 node types, including requestRoll and setQuestStatus. It checks both roll visibilities, all six quest statuses and continuing execution without drawing dice or changing journals. This verifies document shape and predicted actions. Test behavior is still needed to check real targets, authorization and the complete server chain.

    requestRoll validates its dice expression, label, visibility (public or gm) and audience, but only predicts a prompt. Eligible recipients explicitly roll through the native window; streamers receive no roll request. setQuestStatus binds an existing campaign quest and accepts draft, available, active, completed, failed or archived. Live execution uses an active GM authority through the journal service; interacting players gain no general journal editing permission. A synthetic UUID in resources.quest is not proof of quest ownership. The checker resumes Delay through the real continuation and evaluates Counter twice while preserving memory. Interact, Emit event and Timer request later work: the local evaluator does not execute receiver graphs. Teleport requires a real triggering token; invented browser context does not authorize movement.

    Test as GM and player

    Run Simulate to inspect one local event. Then use Test behavior to rehearse through the server; its changes are rolled back. Generate or update the scene as GM, then test a synthetic scene with a GM and an authorized player. Verify that a streamer cannot write. After editing the project again, use Update scene before expecting different live behavior.

    For Target nodes, test a compatible real resource, a missing UUID and a resource from another campaign. For messages/handouts, test trigger audience and a second player. For memory/time, repeat with the same node and then intentionally reset memory through GM controls. Inspect every action outcome in Automation, including unsupported targets.

    How to use AI to adapt any node

    text
    I target Gravewright 0.3.2, source 04f0c1e. Adapt the complete Blueprint for node [type] to [goal]. Inspect blueprints.py, blueprint_runtime.py and the Map Builder guide. Distinguish document validation, evaluator prediction and server application. Select a compatible owner/Target and campaign-owned resources. Return complete JSON, editor steps, expected result and GM/player tests for missing target, permission denial and repetition. Preserve typed ports, memory and continuations where relevant.
