Capabilities: scenes and tokens

This page documents 16 capabilities individually. A capability is an API gate, not a privilege escalation: every operation remains subject to server-side authorization.

tokens.mappings

Authority level: UI · Status: stable · Surfaces: manifest, backend

What it authorizes

Provide token mappings.

When to use it

This is a declarative capability. Use it when the corresponding block is present in the manifest or provides section.

What it does NOT authorize

It validates and enables metadata consumed by the core, but it does not create a JavaScript method on the sdk object.

Declaring a capability does not elevate the user, bypass ownership, or switch context to another campaign.

Available methods

No runtime method. This capability is consumed through the manifest or declarative files.

User permission requirements

The package must be installed, enabled, and active. Operations remain bounded by the current user's context and role.

Minimal example

"capabilities": ["tokens.mappings"]

This capability is consumed by the manifest or descriptor; there is no sdk.tokens.mappings method.

Possible errors

  • CAPABILITY_REQUIRED: capability missing or method gated
  • NOT_FOUND: resource missing, hidden, or outside the campaign

Security and visibility filtering

Yes. The backend projects the response according to campaign, role, ownership, resource visibility, and layer. An omitted resource may be hidden rather than nonexistent.

Lifecycle and teardown

No special teardown is required. Await asynchronous runtime operations and handle the possibility that the campaign or resource changes before completion.

Related capabilities

tokens.read, tokens.move, tokens.manage, actors.read, scene.read

Do not use it this way: Do not call the capability name as an sdk method, and do not declare the gate without providing its required document or descriptor.

scene.geometry.write

Authority level: ADMIN-LIKE · Status: experimental · Surfaces: manifest, backend, frontend, doctor

What it authorizes

Manage logical scene walls, doors and lights.

When to use it

Use it to create, update, split, move, or delete walls; change doors; and create, update, or delete lights as logical scene geometry.

What it does NOT authorize

It does not expose PIXI, RenderTexture, lighting layers, shaders, GPU buffers, the internal canvas, or any renderer object. It also does not bypass GM authority over the scene.

Declaring a capability does not elevate the user, bypass ownership, or switch context to another campaign.

Available methods

  • sdk.scene.geometry.createWall
  • sdk.scene.geometry.updateWall
  • sdk.scene.geometry.deleteWall
  • sdk.scene.geometry.splitWall
  • sdk.scene.geometry.moveWallNode
  • sdk.scene.geometry.moveWalls

  • sdk.scene.geometry.createLight
  • sdk.scene.geometry.updateLight
  • sdk.scene.geometry.deleteLight
  • sdk.scene.geometry.setDoorState

User permission requirements

Normally requires GM or scene-editing authority. The scene must belong to the active campaign.

Minimal example

"capabilities": ["scene.geometry.write"]

await sdk.scene.geometry.createWall(sceneId, wallInput);
await sdk.scene.geometry.setDoorState(sceneId, wallId, "open");

  • STALE_VERSION / CONFLICT: version or state changed before the write

Security and visibility filtering

Yes. The backend projects the response according to campaign, role, ownership, resource visibility, and layer. An omitted resource may be hidden rather than nonexistent.

Lifecycle and teardown

No special teardown is required. Await asynchronous runtime operations and handle the possibility that the campaign or resource changes before completion.

Related capabilities

scene.read, scene.geometry.read, scene.effects.read, scene.effects.write, scene.fog.read, scene.fog.write, scene.images.read, scene.images.write
